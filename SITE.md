# Site: Quiet Grid Press (public website)

Local copy of the public site (Astro). Edited here, pushed to GitHub, pulled by the hosting system (Netlify).
Path: `/Users/scoton/01_ai_workzone/03_qgp_books/04_tools/qgp_website`.
Registered on the Local Site Manager dashboard as `qgp-website` (group QGP, port 4321).
Before first run: `npm install`.

The site is the reference implementation of the brand: palette and fonts in `src/styles/global.css` match the adopted palette and font roles in `../../02_brand/brand_kit.html` (§05 · Visual Identity); the logo in the header (Evergreen on Cream) and footer (inverted on Evergreen Deep) matches that same section's adopted color palette. When building anything new for another channel, check this site's components first.

Book facts (title, subtitle, description, ISBN, ASIN, Amazon page, website page) come from the book catalog, `../../01_plan/qgp_book_catalog.md`. Read the book's entry there before changing a book page; a fact marked "not recorded" is not put on the site.

Content: book pages in `src/pages/books/`; the contact page states the business location, which should be confirmed with the founder.

Phone and desktop, side by side: `preview_phone_desktop.html` in this folder shows the site as a phone (390 x 844) and as a desktop (1280 wide) on one page, with a Both / Phone / Desktop switch, a Local preview / Live site switch, links that move both views to the same page, and Reload both. It is not in `src/` or `public/`, so it is never part of the public build. The dashboard serves a copy at `http://127.0.0.1:3199/artifact/qgp_website_phone_desktop/` (site `qgp-website-phone-desktop`, group QGP); after a change, copy the file to `01_workspace_tools/01_local_site_manager/artifact/qgp_website_phone_desktop/index.html`. When a page is added to the site, add it to the `PAGES` list in that file.

Common Questions has its own page, `src/pages/faq.astro` (/faq/), linked in the footer under Information. The Contact page carries no questions.

The founder's cards on the About page come from `src/data/founder_cards.json` and rotate by date; the plan is in `06_market/00_imprint/market_founder_cards.md`. The public build shows approved cards only; `npm run dev` also shows drafts and cards on hold, marked as such.

A book that has no ASIN yet (`bible_series.json`) opens Book 1 on Amazon from its button, and its page says so. "Back to top" is in `src/components/Footer.astro`. The class `nowrap` keeps a phrase on one line ("from the King James Version." on book pages, "one puzzle per page." on the home page).

The four "What You Will Find" cards (120, 12, KJV, 100%) are one component, `src/components/BookSpecs.astro`, shown on every Bible Verse Sudoku book page between "Inside the Book" and "Part of a Series". A book whose small line must differ gets `spec_lines` (keys `puzzles`, `themes`, `verses`, `solutions`) in `src/data/bible_series.json`.

Visits and the email form, as the code stands: no visit counter is built into the site. The `data-track="amazon-outbound"` marks on the Amazon buttons are labels only; no script reads them. The one script on the site chooses the founder's cards on the About page. The email sign-up form (`src/components/EmailUpdates.astro`, on the home page) is a Netlify form (`data-netlify="true"`) and the privacy page already describes it. The site is deployed by a push to GitHub (`origin`), which Netlify builds; `.github/workflows/daily-rebuild.yml` asks Netlify for a build each morning.

Privacy page: it has a "Short Links" paragraph, and its effective date is the day of that change. If the push happens on a later day, set the date to the push day first.

Visit counts: the privacy page's "Visit Counts and Cookies" paragraph (written 2026-11-17 on Scott's word, "make this happen") describes Netlify's Web Analytics as Netlify's documentation describes it: counts from server records, no cookie, no client script, unique visitors by IP address within a day, up to 30 days. Scott turns the feature on himself in Netlify; his steps are in the todo `qgp_books_netlify_visit_counts_2026-11-17.md`. Netlify counts only pages it serves (HTML, status 200, 201 or 304); it does not count a redirect. That is why a single-book short link is a small page (`src/pages/[code].astro`, data in `src/data/forward_links.json`, written by `build_redirects.py`) that says where it leads and forwards the reader to Amazon, not a line in `_redirects`. When a book gets its ASIN in `src/data/bible_series.json`, run `python3 build_redirects.py` and the book's links open its own Amazon page.

The blog (`/blog/` and `/blog/<address>/`) is built from the blog drafts in `../../06_market/00_imprint/<campaign>/blog/text_blog_*.md`; the words are changed there, never here. One command, `python3 build_blog.py`, reads the drafts, each post's picture (`<campaign>/assets/blog/market_<c>_blog_<nn>_hero.png`), the day each post goes up (its `blog` entry in `../../08_promo/schedule_holiday_2026.json`) and Scott's verdicts in `06_market/register_campaign_review.json`, and writes `src/data/blog_posts.json` (generated, never edited by hand). A post is marked approved only when Scott has approved its words, its picture and its date on the campaign site, the words have not changed and the date has not moved since, and every book the schedule says it needs is in `live_books` there; only then is its picture copied to `public/images/blog/` (so an approved picture can be fetched by its address a few days before its post is up). An approved post is still held back until its date: the blog pages compare the date with the day the site is built, in Scott's time zone (America/Phoenix), so the morning rebuild (`.github/workflows/daily-rebuild.yml`, 5:00 a.m.) puts a post up on its day with no push. So the order is: Scott approves on the campaign site, `python3 build_blog.py`, `npm run build`, push on his word; after that each post appears on its own date. Run the command again after he approves, rejects or moves a post, and push again. A post shows its schedule date. With no post public, `/blog/` keeps its "Under Construction" page. `npm run dev` also shows the rest: a draft is marked "Draft: not approved, not on the public site" with its planned date and what it waits for, an approved post whose day has not come is marked with the day it goes up, and draft pictures are read straight from the campaign folder (`src/pages/blog/draft-picture/`, which makes nothing in the public build). For a test only, `QGP_BLOG_REGISTER` and `QGP_BLOG_SCHEDULE` may point `build_blog.py` at a pretend register and schedule inside the work zone. The blog's styles are one marked block at the end of `src/styles/global.css`.

Common Questions (`src/pages/faq.astro`): the eleven questions as they stood on 2026-11-17 were approved by Scott that day ("Common question approved"). A later change to an answer is a draft again until he reads it.
